# 検知遅延の改善台帳

**目的**: 地震発生から速報記事の公開までを **30分以内** に収める。

この30分という数字は健一さんの実体験に由来する。北海道胆振東部地震のブラックアウトで
携帯基地局のバッテリーが尽き、**停電から約30分でスマホの電波が途絶えた**。
その30分を過ぎてから記事を出しても、被災した方には届かない。

**運用方針(2026-08-14 健一さん指示)**:
> 毎月のテストを行いながら2番目の問題をその都度修正していく。
> そのうえで直らなければその時に判断します。

毎月1日の `jishin-monitor-monthly-check`(瑞樹側の定期タスク)が実行間隔を実測し、
**未試行の施策を上から1つ適用して**、その結果をこのファイルに追記する。
低リスクな施策を使い切っても30分要件を満たせない場合は、健一さんに判断を仰ぐ。

---

## 測定方法

```bash
gh run list --repo keniti2026/jishin-monitor --workflow=monitor.yml \
  --limit 100 --json createdAt,event --jq '.[]|select(.event=="schedule")|.createdAt'
```

取得した時刻の差分(分)から **中央値・最小・最大・「30分を超えた割合」** を出す。
`event=="schedule"` で絞ること(手動実行 `workflow_dispatch` を混ぜると数字が歪む)。
サンプルは直近3日程度・50件以上を目安にする。

---

## 根本原因(GitHub公式ドキュメント)

> Scheduled events can be delayed during periods of high loads of GitHub Actions workflow runs.
> High load times include the start of every hour.
> **If the load is sufficiently high enough, some queued jobs may be dropped.**
> To decrease the chance of delay, schedule your workflow to run at a different time of the hour.

出典: https://docs.github.com/en/actions/how-tos/troubleshoot-workflows

つまり観測される「間引き」は遅延ではなく **ジョブの破棄**。
無料枠・Publicリポジトリの高頻度cronはこれを受けやすい。

## 施策の候補(上から順に試す。リスクの低い順)

| # | 施策 | リスク | 状態 |
|---|---|---|---|
| 1 | cronを毎時0分・30分を避けた分に変更(`*/5` → `2-59/5`) | 低(設定変更のみ) | **実施済み 2026-08-14** |
| 2 | 監視ワークフローを2本に分け、オフセットをずらす(例 `1-59/10` と `6-59/10`) | 低〜中(破棄が独立に効けば実効間隔が縮む。Actions使用量は増えるがイベント駆動なので規約上は問題なし) | 未実施 |
| 3 | `concurrency` のキュー待ちが遅延に寄与していないか検証し、必要なら外す | 低(実行は数秒で終わるため影響は小さい見込み) | 未実施 |
| 4 | 1回の実行内で短時間だけポーリングを繰り返す(例: 5分間、1分おき) | 中(ランナー占有時間が延びる。**数分程度に留めること**) | 未実施 |

### 🚨 健一さんの判断が要る施策(**瑞樹が勝手に実施しないこと**)

| 施策 | なぜ判断が要るか |
|---|---|
| 外部の無料cronサービスから `repository_dispatch` で起動 | 外部サービスのアカウント作成と **GitHub PATの預け入れ** が必要。認証情報を外部に置く判断は健一さんのもの |
| Actionsのジョブ内で常駐ループ(24時間占有) | 精度は出るが **GitHubの利用規約に触れる恐れがあり、アカウントごと止められると監視が全滅する**。遅延より重い失敗になりうる |

## 実測ログ

### 2026-08-14(基準値・施策1の適用前)

- サンプル: 2026-08-11 00:57 〜 2026-08-13 21:00 UTC、schedule実行 59件
- cron設定: `*/5 * * * *`(毎時0分・30分を含む)
- **間隔: 中央値 64分 / 最小 39分 / 最大 154分**
- **30分を超えた間隔: 58/58 (100%)**
- 判定: **30分要件を満たせていない**。地震発生から公開まで最大2時間半かかりうる。
- 施策1(`2-59/5 * * * *`)を適用。次回測定でその効果を見る。
